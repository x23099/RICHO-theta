# 2026年8月18日 日報

## 1. 概要

本日は、8月22日の広空間実験に向けた実機準備から開始し、KobukiのODOM診断・校正、位置精度回帰、停止時誤発火、実時間TTC接近試験まで実施した。

当初の`/odom`は、その場旋回でもYawと`angular.z`が0のまま、代わりに`linear.x`が変化していた。原因を、旋回に追従しないIMU headingを`use_imu_heading=true`で車輪ODOMへ上書きしていたことと特定した。`use_imu_heading=false`へ変更し、有効車輪間隔を`0.23 m`から`0.2634 m`へ校正した結果、直進1 mと左右360度旋回のholdoutに合格した。修正済みODOMは`bird_eye.py`の録画でも停止・前進・左右旋回を正しく分離できた。

青箱を用いた実験では、P0-A位置精度回帰とP0-B停止時誤発火、P0-C 0.10 m/s接近・後退が合格した。P0-C 0.20 m/s接近は、3/3試行でTTC約4秒の`WARNING`が正常に発生した一方、z約0.65 mから位置推定が反転し、前進中に警告が`PATH`へ戻る問題が判明した。

この問題に対し、警告を無期限に固定せず、短時間だけ保持した後に`UNKNOWN`へ移す有限ヒステリシスを実装した。過去3試行の再生では、警告後・前進中の`PATH`を全試行0フレームにできた。新しい実機holdoutは次回実施する。

## 2. 実施内容

### 2.1 実験前チェックと録画GUI

- `preflight_field_experiment.py`を実機で実行し、Python依存関係、青箱基準設定、保存容量、Git来歴、単体テスト、カメラ、`/odom`をすべてPASSした。
- `bird_eye.py`から、試行ラベル付きで`raw.avi`、`bev.avi`、`detection.avi`、`detections.csv`、`metadata.json`を保存できることを確認した。

- AVIの固定30 fpsに対し、実処理は約25 fpsであることを確認した。動的解析の時刻基準にはAVI再生時間ではなく、CSVの`monotonic_time_sec`を使用する方針を固定した。

### 2.2 Kobuki ODOMの診断

次の事実を確認した。

- `/odom`のPublisherは`/kobuki`の1ノードのみ。
- 当初はその場旋回でも`pose.orientation`と`angular.z`が変化しなかった。
- `/joint_states`は前進時に左右同符号、その場旋回時に逆符号であり、エンコーダ入力は正常だった。
- `/sensors/imu_data`は旋回に追従せず、生IMUも旋回角速度の主値として使用できなかった。
- 実行ノードは`~/kobuki_ws`の`kobuki_node/kobuki_ros_node`で、起動経路は`start_kobuki_ffb.sh -> oit/kobuki_vehicle_launch.py`だった。
- `Odometry::update()`内で、`use_imu_heading=true`の場合に車輪Yawと角速度が無効なIMU値で上書きされていた。

### 2.3 車輪ODOMへの変更と校正

採用した変更は次の2点である。

```text
use_imu_heading: true  -> false
effective wheelbase: 0.23 m -> 0.2634 m
```

車輪半径`0.035 m`は、1 m直進試験の精度が十分だったため変更しなかった。独立した車輪ODOMブリッジは追加せず、既存の`/odom`を利用する方針とした。

変更はKobuki側の2リポジトリへ個別にコミットし、両方で名前付きブランチ`experiment/2026-08-18-odom-calibration`を作成した。

| リポジトリ | コミット | 内容 |
|---|---|---|
| `kobuki_core` | `a9f053cc` | 有効車輪間隔を0.2634 mへ校正 |
| `kobuki_ros` | `3f4305a` | IMU headingを使わず車輪ODOMを使用 |

既存の`kobuki_node-launch.py`変更と未追跡`kobuki_bp_node-launch`には手を加えていない。

### 2.7 P0-C 0.20 m/s接近

中央接近を3回評価した。初回警告までは正常だったが、校正範囲の下限付近で位置推定が破綻した。

| 指標 | 結果 | 判定 |
|---|---:|---|
| 4秒`WARNING` | 3/3試行 | PASS |
| 初回警告時z | 0.688～0.701 m | 記録 |
| 初回警告時TTC | 3.918～3.974 s | PASS |
| TTC発火遅延 | 最大0.472 s | PASS |
| 全移動区間の方向正解率 | 87.56% | FAIL |
| 全移動区間の相対速度MAE | 0.0449 m/s | FAIL |

初回TTCから初回警告までに限定すると方向正解率は3試行すべて100%、相対速度MAEは0.0129～0.0168 m/sだった。その後、z約0.65 mで推定距離が増加方向へ反転し、接近継続中にTTCと`WARNING`が消えた。

したがって、この段階は**初回警告PASS、全接近区間FAIL**とした。従来のz=0.45 m停止限界は校正範囲外なので廃止し、今後は`WARNING`で停止操作を開始し、z=0.65 mを物理停止線とする。

### 2.8 衝突警告ヒステリシス

近距離観測切れで警告が即座に`PATH`へ戻ることを防ぐため、次の状態を実装した。

```text
CLEAR / PATH / WARNING / CRITICAL / WARNING_HOLD / UNKNOWN
```

主要設定:

| 項目 | 値 |
|---|---:|
| 警告TTC | 4.0 s |
| 重大TTC | 2.0 s |
| 警告解除TTC | 5.0 s |
| 警告成立確認 | 3 frames |
| 解除確認 | 3 frames |
| 警告保持 | 最大0.8 s |
| 前進判定 | 0.03 m/s超 |

有効な`CRITICAL`は確認待ちせず即時成立する。確定警告後に観測またはTTCが不明になった場合は、最大0.8秒の`WARNING_HOLD`を経て`UNKNOWN`へ移る。前進中にTTCが算出できないだけでは安全証拠とせず、`PATH`へ戻さない。経路外、TTC 5秒以上、停止・後退のいずれかを3フレーム連続確認すると解除する。

CSVへ、生判定、状態遷移理由、保持時間、観測有効性を追加した。集計CLIにも`WARNING_HOLD`率と`UNKNOWN`率を追加し、過去CSVを再生する評価スクリプトを作成した。

## 6. 判明した課題・制約

1. z=0.65 m未満は現在の位置校正範囲外であり、距離・速度・TTCの正式評価に使用できない。
2. P0-C 0.20 m/sは過去録画再生で改善したが、新規実機holdoutは未実施である。
3. 左`x=-0.40 m`は観測ゲートで全件棄却され、左右経路外判定の正式評価前に診断が必要である。
4. AVIは30 fps固定保存だが実処理は約25 fpsである。動画再生時間をTTCの時刻基準にしない。
5. `UNKNOWN`は安全を意味しない。実験中に表示された場合は前進を継続しない。
6. RICHO-theta側の本日追加したヒステリシス実装、テスト、結果資料は日報作成時点で未コミットである。
7. Kobuki側には本件と無関係な既存launch差分が残っているため、今後も混ぜてコミットしない。
