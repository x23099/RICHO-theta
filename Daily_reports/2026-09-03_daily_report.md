# 2026年9月3日 日報

## 1. 本日の目的と到達点

9月2日に固定した動的TTC評価候補を未使用録画で評価し、0.20 m/s接近時に警告が成立しない原因の診断と修正候補の実装を進めた。

画像から推定した接近速度がODOMに対して約15%小さくなる系統差を確認したため、画像速度とODOM速度のうち安全側の値を選ぶ`conservative`方式を候補として実装した。その結果、静止・後退では誤警告を発生させず、正しい速度で撮り直した0.20 m/s接近では3試行すべてでWARNINGを確認できた。

さらに、追加録画を行わずに次段階へ進む作業として、衝突リスク判定を機器非依存のFFB要求へ変換する仮想FFB処理を実装し、既存録画で再生評価した。現時点ではG923への物理出力、ROS経由のFFB指令、自動停止、速度指令の変更は一切行っていない。

## 4. 原因診断

距離と速度の尺度をODOMに対して比較した。

| 指標 | 結果 |
|---|---:|
| 生の画像距離変化量の尺度（中央値） | 0.845 |
| 試行ごとの尺度範囲 | 0.826～0.867 |
| 線形性 R² | 0.9966～0.9994 |
| 平滑化後の距離尺度 | 0.847 |
| 平滑化後の速度尺度 | 0.825 |
| 速度補正量の目安（逆数） | 1.183 |

ばらつきやKalmanフィルタだけが原因ではなく、画像から得た前後方向の変化量が系統的に小さいことが主因と判断した。ただし、距離`z`と速度`vz`を同じ倍率で補正すると`TTC = z / |vz|`の比はほぼ変わらないため、単純な距離スケール補正だけではWARNING不成立を解決できない。

## 5. TTC速度源の比較と候補実装

### 5.1 方式比較

### 5.2 実装内容

- TTC推定器に速度源`visual`、`odom_static`、`conservative`を追加した。
- ODOMが欠落した場合は画像速度へフォールバックする。
- production既定値は`visual`のまま維持し、候補設定を分離した。
- CSVへ画像平滑化速度、実際の採用速度、採用速度源を記録するようにした。
- 画面表示へ採用速度源を追加した。
- preflightで設定と評価プロファイルの不一致を検出するようにした。
- metadata、フレームCSV、評価プロファイル間で速度源一致率95%以上を検証するようにした。
- 通常接近で`WARNING_HOLD`を必須にせず、遮蔽を伴うHOLD評価は別条件として扱った。

## 7. ODOM量子化を考慮したv5診断候補

録画内のODOM速度値の刻みは0.002132～0.002133 m/sだった。この半量子化幅0.001066 m/sを測定分解能として明示するv5候補を作成した。

- `odom_speed_resolution_mps = 0.002132`
- TTC、WARNING、追跡、速度源に関する条件はv4から変更なし
- 同じ`202609031610.tar.xz`への診断再生では3/3 PASS

ただし、これは閾値設計の妥当性を調べるための事後診断であり、独立holdout評価ではない。v5の正式採用には、v5を事前固定した状態で未使用録画へ適用する必要がある。

## 8. 追加録画なしで行った仮想FFB要求生成

衝突リスク判定を、機器に依存しない0～1のFFB要求へ変換する`src/virtual_ffb.py`を追加した。これは既存CSVを再生するだけで、G923、Linux inputデバイス、ROSトピックへは出力しない。

| 再生条件 | activeフレーム | 最大要求 | 起動イベント |
|---|---:|---:|---:|
| 約0.08 m/sだった接近 r01/r02/r03 | 0 / 0 / 0 | 0.00 | 各0 |
| 静止 | 0 | 0.00 | 0 |
| 後退 | 0 | 0.00 | 0 |
| 正しい0.20 m/s接近 r01 | 26 | 0.25 | 1 |
| 正しい0.20 m/s接近 r02 | 22 | 0.25 | 1 |
| 正しい0.20 m/s接近 r03 | 26 | 0.25 | 1 |

`CLEAR`と`PATH`は出力なし、`WARNING`と`WARNING_HOLD`は0.25、`CRITICAL`は0.40とした。不明な状態を無出力にして見逃さないよう、`UNKNOWN`は0.15のパルス要求へ変換する。今回の録画では`CRITICAL`と`UNKNOWN`は発生しなかった。

LinuxカーネルのForce Feedback仕様では、対応能力の確認、effect登録、再生・停止という手順が必要であり、初期化中に機器が強く動く可能性への警告もある。このため、次段階の物理出力では、能力の読み取り、明示的な有効化、最大ゲイン制限、watchdog、終了時と通信断時のゼロ出力を実装してから、停止状態・最小強度で確認する。
