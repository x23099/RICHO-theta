# 広い床4点＋別の検証点を保存する手順（2026-11-09）

## 今回すること

車体・カメラを静止させたまま、**床に離して置く4つの十字**と、校正に使わない**別の十字**を撮る。小さい紙1枚の4隅ではなく、約80×80cmに広がる既知の床4点を使うための追加データ収集である。

まずP0の2枚を提出して、4点すべての視認性を確認する。確認前に10枚全てを撮り切る必要はない。最初から十字が小さい・反射する・見切れる場合はそこで止める。同じ不足を残したまま録画量だけ増やさない。

今回コーン・YOLO・距離表示・Lキー・模擬ODOM・走行・FFBは不要。**以下は画像保存専用の受信器**であり、距離が表示されなくて正常。旧床モデルを読み込まず、既存の保存機能をそのまま使う。コード更新やGit操作は不要。

## 1. 用意するもの

- 白いA4用紙5枚。4枚は固定A～D、1枚は移動する検証点E。
- 印刷する場合は [A4十字PDF（A～E、5ページ）](floor_cross_markers_A4_A-E.pdf) を使える。A4・片面・倍率100%（実際のサイズ）で、「ページに合わせる」を無効にする。全幅14cm・線幅2cm。下部の確認線が10cmか実測し、中央の太い十字の交点を基準にする。まずA～Dを使い、EはP0確認後に使う。
- 黒い太ペン等で、各紙に全幅12～15cm、線幅約2cmの大きな `＋` を1つ描く。線の中心が交わる位置が基準点。小さいV字の先端や細い線にはしない。
- 紙の端へA/B/C/D/Eの識別文字を書く。文字は十字から離し、中央に重ねない。
- 巻尺、床へ平らに軽く固定するテープ。紙を板に乗せず、床へ直接置く。しわ・浮き上がり・段差を避ける。

黒テープを使う場合も、測るのは**十字を作る2本の線の中心の交点**である。今回の基準は紙の左端・紙の角・コーン台座ではない。十字のサイズは視認用で、校正寸法は下記の床上配置の実測値を使う。十字が小さく潰れて見えたら、座標を推測して進めずP0で相談する。

## 2. 原点・配置を決める

原点Oは、従来測距に使っていた**車体中心の床への投影位置**。前方をZ、車体から見て右をX正、左をX負とする。このX/Zは操作者用の平面座標名であり、内部光学座標やROSの軸名と同一という意味ではない。

カメラ直下と車体中心の一致は今回も仮定しない。原点がどこかをメモし、可能なら巻尺・車体と位置関係が分かる写真を添える。カメラ高さは当日測れればレンズ中心までの実測値を記載し、59cmを再測していなければ「以前の申告59cmの持越し」と書く。

解析へ渡す際は、この操作者用の（X右、Z前）を既存の床座標（x前、y左、z上）へ **（x,y,z）=（Z,−X,0）** と明示変換する。左右の符号や前方/鉛直の名称を暗黙に入れ替えない。

|印|役割|左右X|前方Z|
|---|---|---:|---:|
|A|校正・近い左|−0.40m|1.00m|
|B|校正・近い右|+0.40m|1.00m|
|C|校正・遠い左|−0.40m|1.80m|
|D|校正・遠い右|+0.40m|1.80m|

全て**十字の交点まで**測る。Zは斜めの巻尺距離ではなく前方への距離で、左右へ40cmずらしてもZは変えない。A–B、C–D、A–C、B–Dの交点間が約80cmの長方形になる。目標値へ厳密に置けなかった場合は実測値と測定の粗さをメモし、目標値を測定済み値として報告しない。

```text
                  前方（Z）
              P2：E（0,2.00）

 C（−.40,1.80）              D（+.40,1.80）

 P3：E（−.20,1.40） P1：E（0,1.40） P4：E（+.20,1.40）

 A（−.40,1.00）              B（+.40,1.00）

                  O：車体中心
```

Eは1枚を各位置へ順に移す。図のEを4枚同時に用意する意味ではない。A～Dは撮影中ずっと同じ場所に残す。カメラ固定・USBキャプチャ・解像度・向きを途中で変えない。

## 3. GPU/受信PCで起動する

対象：`hsr-Alienware-m16-R2`。既存の距離受信GUIをQ、既存送信をmatunucのCtrl+Cで正常終了する。同じ5002番ポートに2つの受信器を起動しない。`bird_eye.py`等でカメラを同時使用しない。

下記出力フォルダは未使用名を使う。既存なら、削除せず `r02` などへ変更し、以後のコマンドも同じ名前へ揃える。**FLOOR_RUN自体を先にmkdirしない**。本手順の日付は11/9で、別日に実施する場合は全箇所を実施日へ揃える。

```bash
cd ~/yopi_ws/RICHO-theta
export THETA_RTC_PYTHON="$PWD/yolo-env/bin/python3"
FLOOR_RUN="$PWD/recordings/2026-11-09/floor_reference_wide_r01"
echo "$FLOOR_RUN"
"$THETA_RTC_PYTHON" src/theta_rtc_diagnostic.py receive \
  --output-dir "$FLOOR_RUN"
```

受信GUIが開く。送信前は黒画面で正常。これは `start_cone_distance.sh receive` ではないので、YOLO weightsの指定・CUDA処理は不要。

## 4. matunuc/カメラPCで送信する

対象：`matunuc-NUC13ANHi5`、`~/theta_ws`。

```bash
cd ~/theta_ws
export THETA_RTC_PYTHON="$PWD/theta-env/bin/python3"
bash src/start_theta_stream_rtc.sh --diagnostic \
  --receiver-ip 150.89.169.78 \
  --device /dev/video0 \
  --fps 30
```

IPは以前のGPU PCの値。GPU PCで `hostname -I` を実行し、違えば置換する。カメラdeviceが異なる場合はmatunucで `v4l2-ctl --list-devices` を確認して置換する。`--diagnostic`は1回だけで、通常1920×960の送信経路へ切り替えない。

GPU側に左右2眼の実映像が出ることを確認する。`No Signal`、黒画面、過去の静止画が表示されている状態では撮影しない。`ICE completed`だけでは撮影成功と判定しない。

## 5. まずP0を2枚保存する

1. A～Dを配置し、Eはまだ置かない。人・巻尺を基準点に重ねず、2秒ほど静止させる。
2. GPU受信画面の**左レンズ内にA～Dの4つの交点が全部見える**か確認する。車体・機材・人で隠れる、白飛びする、画像端にかかる場合はここで止める。カメラの向きや高さで無理に合わせない。
3. 受信ウィンドウへフォーカスして `S` を1回押す。1秒以上待ち、もう1回 `S` を押す。
4. ターミナルに `Saved decoded frame: ...decoded_<session>_fNNNNNN.png` が2回出ることを確認する。

**Sを押すのはターミナルではなく受信ウィンドウ上**。GUIのスクリーンショットや表示画像の右クリック保存にはしない。S保存は元1280×720の受信フレームで、GUI文字・拡大表示を焼き込まない。元PNGを加工・改名しない。

GPUの別ターミナルで保存を確認する。別端末へ変数は引き継がれないので、同じパスを明示する。

```bash
cd ~/yopi_ws/RICHO-theta
FLOOR_RUN="$PWD/recordings/2026-11-09/floor_reference_wide_r01"
find "$FLOOR_RUN" -maxdepth 1 -type f -name 'decoded_*.png' -printf '%f\n' | sort
```

2つのPNGが表示されれば、**まずこの2枚とA～Dの実測値を提出して、一度視認性を確認する**。この段階では受信・送信を維持して構わない。返答を待つ間に保存フォルダを消したり、別sessionのモデルを読み込んだりしない。再接続が必要なら新しい出力先を使い、P0も撮り直して混在を防ぐ。

## 6. P0の視認性確認後に撮る検証点

この節はP0確認後に行う。A～Dは固定し、Eだけを順に移動する。各位置で静止2秒→S→1秒待つ→S。Eの位置は校正のfitには使わず、後から既知位置と照合するために残す。

|段階|Eの交点位置（X,Z）|保存するもの|累計PNG目安|
|---|---|---|---:|
|P0|Eなし|校正A～Dが全て写る画像2枚|2|
|P1|（0,1.40m）|A～D＋中央検証点Eを2枚|4|
|P2|（0,2.00m）|A～D＋遠方検証点Eを2枚|6|
|P3|（−0.20m,1.40m）|A～D＋左の検証点Eを2枚|8|
|P4|（+0.20m,1.40m）|A～D＋右の検証点Eを2枚|10|

実測値が異なればその値を記録する。P2のEが小さくて交点を判別できなければ、そのまま1枚残して状況を伝え、正しい位置として推測しない。既存のA～Dを動かしたり、画像を拡大再保存したりして補わない。

各段階の直後、別ターミナルで次を実行すれば直近2枚のファイル名が分かる。段階P0～P4と対応させてメモする。

```bash
ls -1t "$FLOOR_RUN"/decoded_*.png | head -n 2
```

余分にSを押してもPNGを削除する必要はないが、どの配置かメモする。ファイル名・点名・実測位置の対応は [capture_notes_template.md](capture_notes_template.md) を参考に、別テキストや紙へ記録する。画像上には書き込まない。

## 7. 終了・提出

P0の最初の確認にはPNG2枚＋実測メモだけでよい。全段階終了時は、GPU受信画面でQ、matunuc送信ターミナルでCtrl+C。受信の終了処理が戻るまで待つ。

GPUの確認端末で、実際のFLOOR_RUNを使う。

```bash
find "$FLOOR_RUN" -maxdepth 1 -type f -name 'decoded_*.png' | wc -l
ls -l "$FLOOR_RUN/received_frames.csv" "$FLOOR_RUN/intake_summary.json"
```

全段階を撮った場合はPNG10枚以上＋CSV＋summaryを確認する。途中段階だけなら枚数はその段階分でよい。保存が確認できなければ「撮れた」と扱わず、終了ログと実際のファイル一覧を伝える。

全段階の提出は**このrecordings側のフォルダ全体**と実測・配置メモ。`Experimental_results`の解析結果フォルダではない。必要ならGPUで、未使用の時刻付きアーカイブを作る。

```bash
ARCHIVE="$HOME/Downloads/floor_reference_wide_$(date +%Y%m%d_%H%M%S).tar.xz"
if test -e "$ARCHIVE"; then
  echo "既存アーカイブがあります。別名を使ってください"
else
  tar -cJf "$ARCHIVE" -C "$(dirname "$FLOOR_RUN")" "$(basename "$FLOOR_RUN")"
  echo "$ARCHIVE"
fi
```

## この撮影で確認できる範囲

既存の `src/floor_reference_pose.py` は、native KB4画素から光線を作り、対応する4点以上の平面座標でIPPEの複数解を保持する。今回変えるのは**収集する床上の物理対応点の配置**で、実行時アルゴリズムを変更したり、通常のピンホール式を生魚眼画素へ直接適用したりするものではない。[OpenCV公式PnP資料](https://docs.opencv.org/4.13.0/d5/d1f/calib3d_solvePnP.html) も既知3D点・画像対応と、IPPEの平面点条件を説明している。

4点を広く置けば必ず精度が出る、と保証する手順ではない。マーカー中心の読取り、配置測量、内部校正の整合性を、校正に使わないEの点で確認するための**実験案**である。P0で視認性を確認し、測定の不確かさも記録してから解析する。

S保存は**WebRTC受信後の無加工PNG**で、通信時の圧縮影響は含む。センサ直結の無圧縮RAWや連続動画を保存したとは呼ばない。今回の目的には静止PNGを使い、原ファイル・session/frame名・CSVの来歴を維持する。現段階で距離完成・走行/FFB承認とはしない。

## 手順の検証範囲

既存のreceive/send CLI定義、receive保存処理、S/Qキー、親フォルダ作成、新規出力条件をソースで確認した。receive/send引数を既存parserで非起動検査し、送信wrapperも `bash -n` で構文確認済み。検査時にカメラ・ネットワークを開かず、撮影出力フォルダも作成していない。実カメラ・ネットワーク・配置の可視性はこのPCで未確認のため、P0が最初の実機確認となる。runtimeコード・安全機構・Gitには変更を加えていない。
