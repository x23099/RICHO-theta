# 保留原因の分解と処理完了を待つ模擬再生

## 結論

追加録画なしで、**姿勢観測の不足**と**姿勢処理が終わるまでの遅れ**を分離した。
姿勢保持の期限や閾値を緩めず、新しい入力が処理中なら診断距離を保留する対照も実装・検証した。
本番やハンコンへ接続した機能ではなく、実験フォルダ内だけの解析実装。

- 従来1,107 frameから因果的再生で失われた730 frameは、最新scene画像の不採用によるものだった。
- このPCのscene抽出＋方向推定は中央値**266.7 ms**、p95 **300.9 ms**。
- 完了を待つ条件で診断距離は377→271 frame。さらに新しい入力の処理中に保留すると**265 frame**。
- 拒否結果が未完了の間に古い姿勢を使った3 frameを、未来の採否を参照せず保留できた。
- 新規**24テストPASS**。原画像・本番・実機・ROS/TF/FFBは変更なし。

## 1. 距離を出せなくなった理由を重複なしで分解

母集団は従来の一括処理で診断距離が出た1,107 frame。
前回の全6,876 frameに対する重複可能な不足理由とは違い、下表は重複しない。

| 前回の因果的対照 | 保持 | 最新scene画像が不採用 | 当該frameにscene sampleなし | 合計 |
|---|---:|---:|---:|---:|
| scene確認frameのみ | 12 | 730 | 365 | 1,107 |
| 最新の有効scene確認から最大1秒 | 377 | 730 | 0 | 1,107 |

この母集団では、730 frameの損失を画像品質や1秒期限切れのせいにはできない。
scene不採用が主要因で、保持を延ばすだけでは物理的根拠を回復しない。
730枚のscene画像が不採用だったという意味でもない。最新sample不採用の状態が続いた**コーン台帳frame数**。

[重複しない損失表](results_r01/historical_loss_partition.csv)

## 2. 保存処理時間を新しいscene遅延と混同しない

9録画14,526 frameの処理時間9列を確認し、全行が有限・非負だった。
同一姿勢系列では、従来処理全体の中央値30.676 ms、青箱pipeline中央値2.336 ms。
これらは**新しいscene解析の時間ではない**。

- `time_sec`はblue処理開始付近の相対monotonic時刻で、カメラ露光時刻ではない。
- totalは処理開始からCSV書込み直前まで。起点が違うため、`time_sec + total`を実測完了時刻としない。
- CSVには露光/取り込み完了/今回scene完了の絶対時刻がない。
- 現コードの時刻経路とmetadataを照合。時刻算出のGit由来は`4056a6b`、blue時刻取得は`1dce82b6`。
  実験当日の全ソフト状態や輸送遅延まで復元したという意味ではない。

根拠：[時刻算出を含む記録実装](../../../src/bird_eye.py)、[処理時間schema](../../../src/frame_timing.py)、
[録画別時間集計](benchmark_r01/recorded_timing_summary.csv)、[全処理時間行](benchmark_r01/recorded_timing_rows.csv)。

初期化できた録画の固定52画像を3周。画像読込みは計測外、warmup1枚、CPUのscene抽出＋infer_upのみ。
OpenCVは当該プロセスで1thread、OPENBLAS_NUM_THREADS=1。画像採否・方向が旧単一frame結果と一致することも全156回確認した。

| 測定 | 値 |
|---|---:|
| 現在PC | robo25-NUC11PAHi5 |
| 固定画像 / 反復 | 52 / 各3回 |
| scene処理中央値 | 266.686 ms |
| p95 | 300.941 ms |

これは現在PCのCPU処理コスト。実験当日のKobukiPC、GPU、YOLO、カメラ入力・伝送・FFB遅延を測った値ではない。
3回の最大値も最悪実行時間保証ではない。全パイプラインの30 fps性能をこの測定から主張しない。

## 4. 結果は処理完了まで使えない、とした比較

scene画像をFIFO単一workerで処理する仮定を固定。保存CSV時刻を模擬入力のrelease時刻と定義し、
`finish=max(release,previous_finish)+service`で完了時刻を作る。
処理済み結果だけを初期化器へ渡し、鮮度は**元入力時刻から**計算する。完了時刻で若返らせない。

現在frameのコーン端点/品質と距離計算はコスト0の比較であり、実験当日の実測遅延再現ではない。
同じframe全体をバッファしてscene結果を待つ運用も試していない。
処理時間を含めた条件はこの1録画1,547 frameに限定。他8録画への性能転用はしない。

| scene処理時間の対照 | 診断距離frame | 0時間対照から保持 | 失ったframe | 追加frame |
|---|---:|---:|---:|---:|
| 0（前回再現） | 377 | 377 | 0 | 0 |
| 画像ごとの実測3回中央値 | 271 | 268 | 109 | 3 |
| 画像ごとの実測3回最大 | 264 | 261 | 116 | 3 |

0時間対照は前回の全1,547 frameの採否・値と完全一致。
今回の1秒間隔入力では各対照ともworkerのqueue待ちは0。
バックログがなくても処理中の結果はまだ使えず、利用可能時間が減る。
初期化を証明する入力時刻は10.057164秒、中央値条件での完了は10.344121秒、
次のframe判断から見える時刻は10.373905秒だった。いずれも録画内の相対時刻。

追加3 frameはframe630/987/1198。
新しい拒否画像が入力済みでもまだ処理完了せず、直前の姿勢が1秒以内なので使われた箇所。
正しい測距が増えた3件とは数えず、未完了拒否があることを事後診断欄へ明記した。
拒否を撮影時点で既に知っていたかのように処理すると、未来参照になる。

## 5. 未完了入力があるとき保留する対照

前節の3件を観察した後で定義した[追加対照](pending_hold_method.md)。最初から事前登録していたとは表現しない。
必要なのは「入力済みの最新frame番号」と「完了済みの最新frame番号」だけで、将来の採否や方向は読まない。
最新入力が未完了なら診断欄を保留する。元の生計算値と姿勢候補は監査用に残す。

| 対照 | 保留追加前 | 保留追加後 | 新たに保留 | 未完了拒否中の出力 |
|---|---:|---:|---:|---:|
| 0時間 | 377 | 377 | 0 | 0 |
| 実測中央値 | 271 | **265** | 6 | **0** |
| 実測観測最大 | 264 | **258** | 6 | **0** |

除くのは3件だけでなく6件。処理中はその画像が将来採用されるかも分からないため、
後で拒否される画像だけを選んで保留することはしない。
新しい幾何や値を作らず、利用可能性を減らすだけの対照。
本番の安全ゲートを変更したものでも、運用許可したものでもない。
