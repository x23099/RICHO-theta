## 性能の推移

| 比較ON時の指標 | r01（削減前） | r02（二重抽出削減） | r03（診断コピー削減） |
|---|---:|---:|---:|
| 主処理P50 | 45.69 ms | 33.51 ms | 27.68 ms |
| 主処理P95 | 67.23 ms | 55.59 ms | 45.22 ms |
| 測定blockの処理件数/秒 | 20.05 | 23.86 | 26.54 |
| 主処理33.33ms超過 | 201/320 | 166/320 | 119/320 |
| 比較service P50 | 43.59 ms | 24.13 ms | 18.81 ms |
| 比較service P95 | 64.45 ms | 34.96 ms | 26.15 ms |
| 模擬入力から比較完了までP95 | 177.46 ms | 93.67 ms | 71.35 ms |

直前r02比で主処理中央値は17.4%短縮、P95は18.7%短縮、処理件数/秒は11.2%増加。主処理33.33ms超過は37.19%残っている。今回のON各blockの主処理P95は45.38／44.79msで、両方とも33.33msより長い。

今回の比較OFFは主処理P50=22.78ms、P95=26.44ms、処理速度29.62件/秒。OFFの中央値は前回22.51msと近い。ON/OFFの差はなお残る。tap自体のP95は約0.034ms、比較完了時ageの最大は146.61msで、全比較行は既存500msの鮮度範囲内。500ms以内であることと30件/秒で処理できることは別である。

件数/秒は320測定行÷2 blockの経過秒合計。P50/P95はnearest-rank。GPU/torch/CUDA/numpy/OpenCV/ultralytics等の記録バージョン、重み、入力のSHAはr02と同じ。ただし温度・電力制限・他プロセス負荷等を同時測定していないため、差の全てをコピー削減だけへ厳密に帰属させない。

8枚を上限30回/秒で反復した保存画像試験であり、自然な連続動画・実カメラ入力・通信／表示／操縦込み遅延の測定ではない。producerが処理遅れに合わせて待つため、実カメラ30fps入力時のdropや追加遅延を直接検証したものではない。モデル初期化約2939ms、warmup初回約959msは測定分布から除外済み。

## 判断・次の範囲

診断コピー削減は、検証した標本で判定を変えずに速度を改善できた。ただし**追加比較を毎フレーム行う条件で30件/秒が維持できたとはまだ言わない。** 主測距そのものが使えないという意味でもなく、追加比較ON時のCPU資源共有を別に扱う。

現時点で追加撮影、同じ未変更コードのGPU再試験、パッチ再適用は不要。次は保存データで、残るCPU処理の内訳と「比較だけの実行頻度」を主測距優先の観点で検討できる。今回の提出監査では、その対策の追加実装や頻度変更は行っていない。参照の失効・主判定・棄却条件・過去値を保持しない方針は維持する。

主表示・操縦・ROS・FFBへ比較数値は引き続き未接続。新たな対策が必要な場合はローカルで検証してから変更後だけGPU確認し、その後に現在カメラの静止実映像を確認する。matunucが使えない状況で新しい撮影や走行は要求しない。
