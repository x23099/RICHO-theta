# 比較処理の負荷内訳と同一フレーム内の計算共有

2026-11-11。GPU提出物では比較ON時に主処理P95が27.07→67.23msへ増えた。原因全体を断定せず、まず保存native8画像と実CUDAが返した新しい枠を使い、CPU側の仕事量を計測する。

1. 既存streamの比較部は `compare_guarded_lower_edge` 内で上側補完観測を作り、直後のbaseline再現engineでも同じ観測を再計算している。主測距側とは別に、比較側だけで同じ元画素・同じ枠の抽出を2回実行する構造を確認する。
2. 既存runtimeはまだ変更せず、独立した録画後計算候補を作る。比較関数自身が今回の元画像から新しく計算したbaseline観測を、baseline距離の再現にも渡す。主ログの観測、別フレーム、前回結果は再利用しない。独立した再抽出と主ログとの一致チェックを維持する。
3. 元方式／計算共有候補を保存8ケースと合成条件で比較し、baseline／proposal／棄却理由／フラグの完全一致・入力不変・改変主行拒否を確認する。
4. CPU計算のOFF→共有→共有→OFF順で、初期化とwarmupを除外したwall時間とcProfile内訳を記録。元8画像を変形・描画しない。このPCの時間をGPU PCでの改善量や30fps達成とは呼ばない。
5. 結果に応じて既存streamへ接続する方法と、主側を止めない頻度／資源分離を次に判断する。CPU/GIL/OpenCV等の原因の切り分けをせずにthread設定を全体変更したり、比較を別processへ移したりしない。カメラ／ROS／機体／CUDAの起動、commit/push、追加撮影は今回行わない。

## CPU候補確認後の接続

保存8ケースは完全一致、新規14テスト成功、抽出16→8回・CPU計算P50 103.88→61.78msを確認した。この範囲に限定して既定OFFの比較worker内部へ接続する。`MotionRangeEngine.measure` に呼出し単位のobserverを追加し、比較関数が同一画像・同一枠から新しく得た観測だけを渡す。通常主測距は未指定の既存observerのまま。engineのframe順序・鮮度・box選択・幾何・主行再現チェックを残し、engineのobserver属性を一時書換えしない。変更した関連コードは過去のハッシュ再利用では済ませず、関係テストと保存画像の実thread再生を再実行する。GPU PCの改善は別に同条件で確認する。
